# Spec 12: Access model, repair verification and an engine-driven 3D model

Scope: the three changes that make Aqua Sentinel's central claim demonstrable. **The AI proposes, the physics checks it, the evidence proves it.** A repair is only "done" when later measurements say so, and the 3D model shows exactly what the real engines concluded, never a rule of its own.

All data in this scope is synthetic (seeded generator + hydraulic solver validated against EPANET). Nothing here claims a field result.

## 1. Access model

- **REQ-ACC-01**: Nobody writes without an account by default. The "open access" guest session (`invitado`, role OPERATOR) is opt-in (`--open` or `AQUA_OPEN_ACCESS=1`), local-development only, and is ignored when `NODE_ENV=production` or public mode is on. The guest can never read users or the audit log.
- **REQ-ACC-02**: In public mode an anonymous visitor can read the demo and nothing else, even if open access is requested. The only public routes are closed-list `GET`s (`/api/state`, `/api/events`, `/api/evidence/:sha256`, `/api/preview/leak`).
- **REQ-ACC-03**: Judges get an `OPERATOR` account defined only through the environment (`AQUA_JUDGE_PASSWORD`, optional `AQUA_JUDGE_USER`). The password must satisfy the normal policy, is never stored in clear text, never logged, and an existing account is never overwritten. The account cannot manage users, read the audit log, import or reset state.

## 2. Repair verification

A closed work order proves nothing by itself. Verification is a pure function (`src/core/repairVerification.ts`) used by the server to decide, by the dossier verifier to recompute, and by the UI to explain.

- **REQ-REP-01**: Only measurements strictly newer than everything the server knew at closing count. Stale, duplicated or future-stamped data cannot prove anything; readings written by the system (`restored`, `baseline`) are never measurements; a frozen sensor cannot verify a repair; arrival order is irrelevant.
- **REQ-REP-02**: `VERIFIED` requires three consecutive usable measurements within normal range **and** a hydraulic balance that no longer shows a leak. One or two measurements are `INCONCLUSIVE`; none is `PENDING`. A hydraulic excess that is not concluded as a leak also blocks verification.
- **REQ-REP-03**: `REOPENED` when two consecutive post-closure measurements are still anomalous, or when the hydraulic balance still concludes a leak. A defective sensor reading is never evidence in either direction and breaks any streak.
- **REQ-REP-04**: Only final verdicts (`REPAIR_VERIFIED`, `REPAIR_REOPENED`) are sealed in the Trust Ledger, together with the readings and the hydraulic gate that support them. The dossier verifier recomputes the verdict from the sealed readings and rejects a chain-valid dossier whose verdict does not follow from its evidence.
- **REQ-REP-05**: The UI shows the sealed verdict first, then the server's provisional assessment, then a local recomputation. Without a sealed verdict a repair is never presented as achieved, and synthetic evidence is labelled as simulated.
- **REQ-REP-06**: To demonstrate the cycle offline, an operator can inject simulated post-closure measurements (`repaired`, `unresolved`, `sparse`). They come from the hydraulic solver, pass through the normal ingestion and the same engines, are ledgered as `SIMULATED_MEASUREMENTS_INJECTED`, and are refused on an instance that holds non-synthetic readings. No verdict is prefabricated.

## 3. Engine-driven 3D model

- **REQ-SIM-01**: The 3D model contains no physics and no thresholds. Every number and conclusion it shows comes from a `LeakPreview`, and the UI only chooses which snapshot belongs to each step and narrates what the engine concluded, including when it refuses to conclude.
- **REQ-SIM-02**: `GET /api/preview/leak` runs the real pipeline (solver, hydraulic diagnosis with its persistence streak, node rules, repair verification) on seeded synthetic data. It is deterministic, read-only, input-bounded, and does not touch server state. Small leaks stay `no_anomaly`; medium leaks are a `flow_anomaly` that the engine does **not** call a leak; only a leak with consistent pressure response is `localized_leak`.

## 4. Spec tooling

- **REQ-KIRO-01**: `npm run verify:kiro` checks real evidence, not file existence. A requirement is verified only if it is defined once, has a traceability row, every file it cites exists, it cites at least one test file, and at least one of those test files mentions the requirement. `npm run lint` or \\erified by compilation\\ does not count as a test.

- **REQ-I18N-01**: The interface is available in English and Spanish from one string table (`src/ui/i18n.ts`, `t(es, en)`), with no duplicated components. The language comes from `?lang=` or the browser, the EN/ES switch is in the header, and the Hero follows it. Text generated by the server or the engine (diagnosis wording, checklist tasks, ledger summaries) stays in Spanish by design; engine codes are explained in the UI through `explainRepair`.

- **REQ-I18N-02**: Text written by the server or the engine (diagnoses, hypotheses, checklist, verification messages, ledger summaries, verifier checks, API errors) is translated only when displayed, by a presentation layer (`src/ui/engineText.ts`). It never changes the engine, the API contracts, the sealed text or any hash. Sentence templates keep every number and identifier; unrecognized text is shown unchanged. A test drives the real server through the full cycle and fails if a displayed sentence still contains Spanish.
